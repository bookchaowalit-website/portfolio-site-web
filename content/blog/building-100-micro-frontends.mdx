When I set out to build my portfolio, I didn't just want a single monolithic app. I wanted to prove a point: **one developer can run a large fleet of independently deployed applications** using modern tooling and a disciplined architecture.

The fleet is still growing, and not every app is production-grade: some are live products, others are prototypes or experiments, and the project gallery labels each one honestly.

## The Architecture

Each micro-frontend is a standalone Next.js application with its own:
- Repository and deployment pipeline
- Custom domain or subdomain (if needed)
- Independent versioning and release cycle

Monitoring is uneven by design: error tracking with Sentry and analytics with PostHog are wired into a subset of the apps, mostly the products that have real users, and are not yet in every app.

## Why Micro-Frontends?

### Independence
Each app can be updated, rolled back, or rebuilt without affecting any other. When I experiment with a new framework or pattern, I can test it in one app first.

### Performance
Small bundles load fast. Most of my tools ship little JavaScript, with no bloated mega-bundle serving unused code to every visitor.

### Learning
Building many apps taught me more than building one big one. Each project is a chance to explore a different pattern: MDX blogs, canvas-based tools, real-time dashboards, AI integrations.

## The Tech Stack

Most projects share a common foundation:
- **Next.js** with App Router
- **TypeScript** for type safety
- **Tailwind CSS** for styling
- **Vercel** for deployment

But each project is free to add its own dependencies based on its needs.

## Key Trade-offs

### The Good
- Changes in one app rarely break another
- Fast deploys, because each app is small
- Easy to archive or sunset projects

### The Challenging
- Shared component libraries require discipline
- Authentication must be solved once and reused
- Analytics and error tracking have to be rolled out app by app, and aggregating them across many domains is still unfinished work

## What I'd Do Differently

If I started over, I would:
1. Create a shared design system package from day one
2. Set up a monorepo with Turborepo earlier
3. Automate more of the project scaffolding
4. Wire in error tracking and analytics at scaffolding time instead of retrofitting them

---

*The best architecture is the one that lets you ship consistently. For a solopreneur, that means independence, speed, and the freedom to experiment without fear.*
